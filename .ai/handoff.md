## 프로젝트 개요

- 신용카드 혜택(실적 허들) 관리용 사용량 대시보드. 단일 파일 `index.html` 하나로 구성되어 있고 별도 빌드 과정이 없다.
- 이 페이지는 **Claude 아티팩트 런타임 전제**로 작성되어 있다. 데이터 저장을 `window.claude.use('db')`(`index.html:701` 부근)에 의존하며, 카드/월/결제 기록이 전부 이 DB에 저장되고 최초 실행 시 `seedInitialData()`가 씨드 데이터를 써 넣는다.
- `window.claude`가 없는 환경(로컬 `file://`, `python3 -m http.server`, GitHub Pages 등)에서 열면 `index.html:697`에서 바로 "이 페이지는 Claude 앱 환경에서 열어야 데이터가 저장됩니다" 배너만 뜨고 **카드가 하나도 렌더되지 않는다.** 레이아웃/폰트 확인 정도만 가능하다.
- 실제로 구동해서 보려면 **Claude 아티팩트로 `db` capability를 선언해 게시**해야 한다. 이번 세션 끝까지 게시는 진행하지 않았다 (사용자에게 제안만 한 상태).

## 이번 세션에서 한 일

1. **씨드 데이터 "변형/복구" 주장 조사** — 사용자가 세션 앞부분에서 "씨드 데이터가 변형되어 복구했다"고 언급했으나, 실제로는:
   - 작업 브랜치가 `main`과 완전히 동일했고 (`git log main..HEAD` 커밋 0개)
   - `index.html`의 git blob 해시가 최초 업로드 커밋 이후 세 커밋 모두 동일 (`cc1da6e...`, 내용 변경 없음)
   - 이 계정에 게시된 아티팩트가 하나도 없었음 (씨드는 아티팩트 DB에 쓰이는 값이라 실제 변형이 있었다면 거기서 일어났어야 함)
   → **변형됐다는 근거도, 복구했다는 흔적도 찾지 못했다.** 씨드 값은 원본 그대로 두었다.

2. **진행 바 계산 버그 발견 및 수정** — `barSegmentsHtml()` 함수(변동 구간 밴드를 그리는 부분, 파일 내에서 `pct(solidEnd+stats.sumMax)` 문자열로 검색하면 위치를 바로 찾을 수 있음)에서 연산자 우선순위 실수:
   ```js
   // 수정 전 (버그) — 전체 삼항 조건이 폭 자체를 결정해버려 항상 pct(sumMax-sumMin)으로 축소됨
   width:' + (pct(solidEnd+stats.sumMax-stats.sumMin>0?stats.sumMax-stats.sumMin:0)) + '%
   // 수정 후
   width:' + (pct(solidEnd+stats.sumMax)-pct(solidEnd)) + '%
   ```
   - 버그 영향: 밴드가 예상 최대 실적(`projectedMax`)보다 짧게 끝남. 씨드의 KB국민 카드 값(허들 300,000 / 고정 13,900 / 변동 130,000~310,000) 기준으로 밴드가 59.86%에서 끊겨, 허들 마커(92.62%)보다 왼쪽에 위치 — `computeStats`가 이 카드를 `likely`(최대치면 허들 달성)로 판정하는데도 시각적으로는 달성 불가능해 보이는 모순이 있었음.
   - 부수 효과: `sumMin > sumMax - sumMin`인 카드에서는 최소 금액 솔리드 오버레이가 빗금 밴드 밖으로 삐져나오는 문제도 함께 있었는데, 이번 수정으로 같이 해소됨.
   - 검증: `computeStats`/`barSegmentsHtml` 두 함수를 파일에서 그대로 추출해 Node로 직접 실행, 씨드 값(KB국민/하나 클럽SK) 포함 4개 케이스(정상 씨드 2개 + `sumMin > delta` 케이스 + 결제 항목 없는 케이스)로 각 div의 `left`/`width`를 파싱해 밴드 끝 지점이 `projectedMax` 비율과 정확히 일치함을 확인했음.
